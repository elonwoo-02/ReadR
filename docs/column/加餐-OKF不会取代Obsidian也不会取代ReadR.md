---

最近 Google Cloud 发布了 OKF（Open Knowledge Format）。

看到这个消息，很多人心里会冒出几个疑问：AI Agent 时代，Markdown 笔记是不是要被重新定义了？Obsidian 这种个人知识库还有价值吗？企业知识库、科研知识库是不是都要被 OKF 取代？

我的判断是：不会。

原因很简单——它们解决的根本不是同一个问题。

## OKF 到底解决什么问题？

过去，知识是给人读的：PDF、Word、Wiki、Notion，格式再怎么变，终点都是人的眼睛。现在，情况变了——Agent 也要读知识。问题从"人能不能搜到"，变成了"Agent 能不能理解"。

OKF 不是一个新的笔记软件，它更像一份写给知识本身的说明书——不是记录知识说了什么，而是记录这份知识**能不能被信任**：它从哪里来、是谁生成的、有没有人确认过、是不是已经过期了。

一句话概括：OKF 解决的是"知识如何被机器理解"。

## 为什么 OKF 不会取代 Obsidian？

Obsidian 解决的是另一个问题：人怎么组织自己的知识。双向链接、图谱视图、长期积累——它关心的是人的思考过程本身，不是"这条笔记能不能被机器信任"。

两者的关系不是谁取代谁，是分工：Obsidian 产生知识，OKF（如果需要）描述知识，AI Agent 消费知识。三件事发生在三个不同的层面上。

就像 Markdown 和编辑器从来不是同一个维度的东西——Markdown 是格式，编辑器是工具，格式变了不代表工具就没用了，工具好用也不代表可以脱离格式存在。OKF 和 Obsidian 是同样的关系。

## 为什么 OKF 也不会取代 ReadR？

这是全文真正想讲清楚的问题。

科研从来不是"找到答案"这么简单的事，是一条具体的路径：

```
sources  →  reading  →  annotation  →  review  →  knowledge
（拿到论文）  （读）      （批注）      （总结）    （形成观点）
```

ReadR 管理的正是这条路径本身，不是路径走到终点之后留下的那个结果。

把两者放在一起对比，差异会更清楚：

| | OKF | ReadR |
|---|---|---|
| 定位 | 知识交换格式 | 科研知识工作流 |
| 用户 | Agent / 企业 | 研究者 |
| 对象 | 知识单元 | 论文生命周期 |
| 重点 | 知识结果 | 知识产生过程 |
| 时间维度 | 新鲜度追踪（这条定义是否过期） | 过程阶段追踪（这篇论文读到哪一步） |
| 价值 | 可复用 | 可演化 |

时间维度这一行值得多说一句，因为很容易被简单地理解成"谁更强"。OKF 这次升级恰恰是把时间维度做成了一等公民——一条知识是什么时候生成的、什么时候该被重新核实，这些现在都能被明确追踪。但它追踪的是**一个静态知识点的新鲜度**：这条定义还站不站得住。ReadR 的时间维度追踪的是完全不同的东西——**一个动态过程走到了哪一步**：这篇论文是刚拿到手,还是已经精读完,还是已经沉淀进了综述。不是谁的时间维度更强，是两者的时间维度在描述完全不同的对象。

这组差异可以浓缩成一句话：

**OKF 回答的是"知识是什么"，ReadR 回答的是"知识是怎么产生的"。**

## ReadR 可以从 OKF 学什么？

有一个方向可以先排除：不需要把 ReadR 的目录结构改成 OKF 的样子，不需要把整个仓库转换成 OKF 格式，也不用急着做一个导出工具。ReadR 的价值不在文件格式本身，在工作流——格式可以借鉴，工作流不需要为了兼容一个新格式而妥协。

真正值得吸收的是 OKF 背后那套知识治理的思路，可以拆成四个问题：

这条知识**来自哪里**——是某篇有 DOI 的论文，还是某个数据集，还是一本书。这条知识**是谁生成的**——是人写的，还是 AI 起草的，还是某个 agent 自动生成的。这条知识**谁确认过**——有没有经过研究者本人或者同行的审核。这条知识**现在还有效吗**——是当前在用的，已经被淘汰的，还是已经过时需要重新核实的。

这四个问题，ReadR 现在只回答了一部分——阅读状态记录了"读到哪一步"，但没有记录"这段内容是人写的还是 AI 起草的、有没有被确认过"。补上这一层，ReadR 会从一个"Markdown 论文库"，变成一个"可审计的科研知识系统"——你可以清楚地知道自己知识库里的每一条笔记，是自己确认过的判断，还是还没来得及review的 AI 草稿。

## 未来三者如何共存？

讲了这么多区别，最后回到一张图上：

```
      ┌─────────────┐          ┌─────────────┐
      │   Obsidian  │          │    ReadR    │
      │  个人知识管理 │          │  科研知识生产 │
      └──────┬──────┘          └──────┬──────┘
             │                        │
             └───────────┬────────────┘
                          ┊
              共享同一个底层选择：
              markdown + frontmatter
                          ┊
              ┌───────────┴───────────┐
              ┊                       ┊
        直接读取原始 markdown      可选：OKF 描述
                                （知识交换规范）
              ┊                       ┊
              └───────────┬───────────┘
                          ┊
                      AI Agent
                GPT / Gemini / Claude
```

注意中间到底部这一段是虚线，不是实心箭头——这不是一条"必须依次经过"的流水线。Agent 完全可以直接读 Obsidian 或 ReadR 生成的原始 markdown，不需要先转换成 OKF 才能被理解；OKF 只是一层可选的、额外的信任描述，需要跨组织交换知识的时候才用得上。

Obsidian 是编辑器，ReadR 是科研工作流，OKF 是交换协议。它们不是竞争关系，而是不同层次的基础设施。

## AI 时代真正重要的是什么

知识库的竞争早就不是"谁存得多"，是"谁的知识生产流程更好"。

OKF 让知识更容易被 AI 理解。ReadR 希望让科研知识更可靠地产生。Obsidian 让个人的思考过程有地方沉淀。三件事各自成立，谁也不需要谁让位。

---

回到标题：OKF 不会取代 Obsidian，也不会取代 ReadR。因为它们分别在解决三个不同的问题——如何记录知识、如何生产知识、如何交换知识。

未来真正强大的知识系统，大概率不会是某一个工具赢家通吃，而是一套组合：

**人负责创造知识，工作流负责沉淀知识，标准负责连接知识，AI 负责使用知识。**
