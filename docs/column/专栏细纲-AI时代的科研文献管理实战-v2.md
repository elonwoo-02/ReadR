## 05｜工具化：从"手工流程"到"三层真实自动化"

**目标（较原版重写）**：原大纲的前提是"项目还没有内置自动化工具"，这个前提已经不成立——现在有三层真实存在的自动化，这一讲要做的是把这三层讲清楚，并且划出每一层各自的边界，而不是再讨论"要不要去搭"。

1. 导读：你将获得
   - 三层自动化工具的全景图：Obsidian 插件层、Claude Code 指令层、NotebookLM CLI 层
   - 每一层各自解决工作流的哪个阶段
   - 一份仍然有效的边界清单：这三层工具分别在哪一步需要人工确认
2. 第一层：Obsidian 插件生态——把重复操作装进侧边栏
   - 五个内置插件：**ReadR Dashboard**（统计看板，需要 `npm install && npm run build` 才能用）、**Dataview**（元数据查询引擎，开箱即用，Dashboard 依赖它）、**RealClaudian**（Obsidian 内直接对话 Claude）、**OTerm**（内嵌终端，不用切窗口就能跑 `pwsh scripts/ReadR.ps1 -Validate`）、**RSS Dashboard**（订阅源自动推送新论文，INGEST 阶段的入口自动化）
   - 强调 Dashboard 和其余四个插件的区别：一个需要自己构建，其余开箱即用——这是这一层自动化目前唯一的门槛
3. 第二层：Claude Code——用自然语言驱动四个阶段
   - `CLAUDE.md` 自动加载，行为规则不需要每次重新交代
   - 四个阶段各给一句可以直接抄的指令（对照 README「Typical Usage」）：
     - INGEST："基于这篇论文的 PDF，用 library/_template/library-entry.md 模板创建条目"
     - BROWSE："提取这篇论文的核心概念，写入 library/concepts/"
     - CLOSE-READ："按 annotations/_template/reading-note.md 模板生成这篇论文的精读笔记初稿"
     - REVIEW："总结这个子方向下的所有论文，写一篇综合概述"
   - 呼应 03 讲：这些指令生成的都是草稿，图表公式仍然要手工嵌入
4. 第三层：NotebookLM CLI——REVIEW 阶段的深水区（本讲只做导览，详细展开留给下一讲）
   - 一句话带过：`notebooklm generate report` 可以直接产出综述初稿的 Markdown 版本
   - 明确这一讲不深入展开，理由：这一层的命令覆盖面和边界值得单独一讲，见 06
5. 三层自动化的共同边界（呼应第三讲的测试）
   - Obsidian 插件层：错误容易发现（统计看错了、订阅源重复了，肉眼可见）
   - Claude Code 层：草稿必须人工确认才落盘，契约里写死了
   - NotebookLM 层：生成内容明确标注为草稿，必须发布前润色——三层自动化没有一层触碰"判断"和"下笔"
6. 小结
   - 自动化已经不是"要不要做"的问题，是"用哪一层、边界在哪"的问题
7. 思考题/练习
   - 打开你自己的 Obsidian，把 ReadR 的五个插件挨个装一遍，记录哪一步卡住了——大概率是 Dashboard 的构建步骤

## 06｜NotebookLM 深度集成：把 REVIEW 阶段接上自动化管线（新增）

**目标**：REVIEW 阶段是整个工作流里人力成本最高的一步，这一讲讲清楚 NotebookLM CLI 能把这一步的哪些部分接上自动化、边界又在哪。

1. 导读：你将获得
   - notebooklm-py 这个 CLI 相对网页版 NotebookLM 多出来的能力范围
   - 一份分类清晰的命令地图：source 管理 / 内容生成 / 内容管理 / 下载 / 对话 / 笔记 / 协作
   - 一份"已知局限"清单，帮你判断什么时候该用、什么时候不该依赖它
2. 为什么 REVIEW 阶段最值得优先自动化
   - 前三个阶段（INGEST/BROWSE/CLOSE-READ）都是"单篇论文"粒度的工作，REVIEW 是"多篇论文综合"的工作——人力成本随论文数量非线性增长，正是最该借工具的地方
   - 但也正因为是综合判断,是"论点"产生的地方,自动化能做的只是把"信息转格式"这一步接管,不能替你下判断（呼应 03 讲的核心论证）
3. notebooklm-py 命令地图,按功能分类过一遍
   - **Source 管理**：`source add`（URL/文本/文件/YouTube 都能加）、`source add-research`（联网搜索自动导入相关资料）、`source guide`（AI 生成摘要和关键词）、`source clean`（自动清理重复或失效的资料）
   - **内容生成**：这是命令最多的一类——`generate report`（生成综述初稿）、`generate slide-deck`（生成幻灯片,支持导出 PDF/PPTX）、`generate audio`（生成播客,支持深度/简讯/评论/辩论四种风格）、`generate mind-map`（生成思维导图）、`generate quiz`/`generate flashcards`（生成测验和记忆卡片，备考或者查漏补缺时有用）
   - **内容管理与下载**：生成的东西都有版本管理（`artifact list/get/retry`），下载格式覆盖 Markdown/CSV/JSON/图片/音视频
   - **对话与协作**：`ask` 基于笔记本里所有资料回答问题，`share` 支持团队协作和权限控制
4. 具体场景演示：组会前一天，把一篇论文变成一份汇报 PPT
   - 对照 README 的 Quick Start：装好 CLI → 建笔记本 → 加论文 → 一条命令生成 slide-deck → 下载 PDF/PPTX
   - 强调这个场景解决的是"信息转格式"的体力活——论文内容到 PPT 排版之间的转换，不是"这篇论文该怎么评价"这种判断
5. 和 Claude Code 的集成
   - `notebooklm skill install --scope user --target claude` 装完之后，可以在 Claude Code 里直接用自然语言触发 NotebookLM 命令（比如直接说"把这篇论文做成播客"）
   - 这一步把 05 讲的第二层（Claude Code）和第三层（NotebookLM）连了起来,不再是两个孤立工具
6. 已知局限，必须诚实交代
   - 笔记本最多容纳 50 个 source，有大小限制——论文攒多了要分笔记本
   - source 只读，没法在里面直接做批注——批注还是要回到 `annotations/`
   - 依赖网络，所有处理都在 Google 服务器上跑
   - 输出质量取决于 PDF 质量,扫描版 OCR 效果会打折扣
   - **生成的报告是草稿**，发布前必须人工审阅和润色——这条和 03 讲"个人评价与思考不能被压缩"是同一条原则在 REVIEW 阶段的体现
7. 小结
   - NotebookLM 接管的是格式转换,不是论点生成；这一层自动化做得再深,写综述这件事的责任人还是你
8. 思考题/练习
   - 挑一篇你已经精读完的论文，用 `notebooklm generate mind-map` 或 `generate slide-deck` 跑一遍，看生成结果里哪些地方需要你手动修正——这些修正点，往往就是这篇论文里真正需要你判断的部分
