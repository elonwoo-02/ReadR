# 05｜工具化：把工作流封装成可复用的 Agent/Skill
![[05.png]]
## 你将获得

- INGEST 阶段自动化的具体实现思路——从 PDF 到带元数据的条目初稿
- 一份自动化边界清单：哪些动作可以封装，哪些必须留给人
- 一个可以现场跟做的最小自动化流程

## 先说清楚现状

ReadR 仓库本身，到目前为止只写清楚了"AI 在哪些环节可以协助"这张表（第三讲已经讲过），并没有内置自动化脚本——README 里给的是手工步骤：下载 PDF、复制模板、手填 frontmatter、浏览时同步提炼概念。这不是一个缺陷，是一个诚实的现状：**方法论先于工具存在，工具是方法论跑顺了之后才值得封装的东西。**

这一讲要做的事，是把前四讲讲清楚的"哪些活可以交给 AI"，从"每次手动做一遍"升级成"写一次、反复调用"。顺序很重要——没有前面三讲的分工边界，自动化只会把错误也一起放大。

## 为什么从 INGEST 阶段开始

四个工作阶段——INGEST（入库）、BROWSE（浏览沉淀）、CLOSE-READ（精读）、REVIEW（产出）——INGEST 是判断成分最少的一环：下载一篇 PDF，提取标题、作者、会议、DOI 这些客观存在的信息，套进 YAML frontmatter 模板。这件事没有"我怎么看这篇论文"的成分，纯粹是信息搬运,天然适合最先自动化。

用 Claude Code 或者任何支持 MCP 的工具，实现思路很直接：

```
PDF 文件
  → 读取前两页文本（标题、作者、摘要通常都在这里）
  → 抽取 title / authors / venue（如果摘要页有会议信息）
  → 尝试匹配 DOI（可选：调用 CrossRef API 按标题反查）
  → 生成带 YAML frontmatter 的 entry 初稿，tags 先留空或打上 status/to-read
  → 落盘到 library/entries/<direction>/，同时把原 PDF 移入 sources/papers/
```

这一步产出的是初稿，不是成品——tags 里的 direction/method/task 还需要你确认，因为这需要你对研究方向的判断，纯文本提取做不到这一层。

## 自动化边界清单

把前几讲的分工原则落到"能不能封装成自动脚本"这个具体问题上：

| 环节 | 能否自动化 | 判断依据 |
|---|---|---|
| 元信息提取（title/authors/venue/DOI） | 完全自动化 | 客观事实，出错会在你确认时被立刻发现 |
| 条目框架生成（YAML + 占位正文） | 完全自动化 | 同上，且格式固定，机械操作 |
| BROWSE 阶段的概念/作者/数据集提取 | 完全自动化 | 第三讲已论证：错误会在精读时被自然拦截 |
| 对比表生成 | 完全自动化 | 同上 |
| syntheses 概述起草 | 生成初稿，人工确认后落盘 | 涉及对多篇论文的归纳判断，AI 起草可以，但下判断的是人 |
| 精读笔记初稿（前五段） | 生成初稿，人工确认后落盘 | 转述性内容，AI 起草+人核对 |
| 个人评价与思考 | 绝不自动化 | 第三讲的核心论证：这类错误不会被后续步骤发现 |
| 综述的论点与结论 | 绝不自动化 | 对读者负责的最终产出 |

这张表不是新规则，是把第三讲那条测试——"错误会不会在后续步骤被自然发现"——套用到"值不值得写脚本"这个新问题上，得到的自然结果。凡是容错空间大的环节，写脚本封装的投入产出比很高；凡是容错空间小的环节，封装本身就是在放大风险，不值得做。

## 该往哪个方向搭：三个具体思路

既然仓库目前还没有内置自动化，这里给三个值得优先动手的方向。

**1. Agent 工作流编排**：把 INGEST → BROWSE 的机械步骤串成一条流水线，而不是每次手动跑一遍脚本。比如用 Claude Code 的 Skill 机制封装成"扔一篇 PDF 进来，自动完成入库+概念提取+对比表更新"的单条命令，人只在最后确认环节介入。

**2. 独立应用/前端**：命令行和 Obsidian 对非技术背景的合作者（比如你的导师、师弟师妹）门槛偏高。一个轻量的 Web 界面——上传 PDF、看到自动生成的条目草稿、点确认——能让这套方法论传播给更多人，而不只是你自己用。

**3. 与现有工具桥接**：很多人已经在用 Zotero 做文献管理，完全推倒重来成本很高。可以考虑做一个同步脚本，把 Zotero 里已有的条目和标注，转换成 ReadR 的 entry 格式，作为迁移路径而不是替换路径。

这三个方向没有先后依赖，看你自己更痛哪一个：如果论文量大到手动 INGEST 已经吃不消，先做第一个；如果想让这套方法论被团队采用，先做第二个；如果历史存量论文已经很多，先做第三个。

## 一个可以现场跟做的最小示例

不需要一上来就搭完整系统，先跑通一个最小闭环，验证思路可行，再决定要不要往上叠功能：

```
输入：一篇 PDF 路径

第一步：用 Claude Code 读 PDF 前两页，提取 title/authors/venue
第二步：把提取结果套进 library-entry.md 模板，tags 先留 status/to-read
第三步：把生成的 entry 展示给你看，你确认或修改
第四步：确认后，脚本把 entry 写入 library/entries/<direction>/，
        同时把 PDF 移动到 sources/papers/
```

四步做完，一篇论文从"下载下来的文件"变成"知识库里有编号、有元数据的条目"，全程你只在第三步花十几秒确认，而不是从头手填一遍 YAML。这个最小闭环跑顺了之后，再往前叠加 BROWSE 阶段的概念提取，逐步把自动化边界清单里"完全自动化"那几行都接进这条流水线。

## 小结

自动化的目标不是替代判断，是把机械劳动交出去，把省下来的时间留给"判断"和"下笔"。判断哪些环节值得封装，用的还是第三讲那条测试——错误会不会被后续步骤自然发现。下一讲是整个专栏的收束：用一个真实的科研方向，把前五讲讲的架构、字段、分工、动作、工具，完整走一遍，看这套方法论到底能不能真的沉淀出一份可发表的综述大纲。

---

**思考题**：挑一个你手工重复做过最多次的动作——可能是复制模板、可能是手填 DOI——对照自动化边界清单，判断它落在哪一档。如果是"完全自动化"这一档，这周花半小时试着写个最小脚本。
