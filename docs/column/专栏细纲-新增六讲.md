## A｜综述写作方法论：从"论文罗列"到"故事线"

**定位**：前七讲讲的是"怎么攒材料"，这一讲讲"材料攒够了之后怎么真正写好"，脱离 ReadR 工具本身，是通用的综述写作方法论。

1. 导读：你将获得
   - 三种综述组织角度的适用场景，不再是"按发表时间顺序写"这一种默认选项
   - 判断一段综述是不是"论文罗列体"的具体标准
   - 从 `syntheses/` 到成稿的转化方法，不是拼贴而是重新组织
2. 从一个反例说起
   - 最常见的失败模式：每段开头都是"XX 等人（年份）提出了……"，读完等于把参考文献逐条复述了一遍，没有作者自己的观点
   - 归因：把"我读过这些论文"当成了"我理解了这个领域"，两者之间还差一步
3. 三种组织角度，分别讲适用场景
   - 按方法演进（technique lineage）：适合方法迭代关系清晰的领域，一条主线讲清楚"为什么下一代方法要解决上一代的什么问题"
   - 按问题维度拆解（problem-oriented）：适合领域内有多个并行子问题，各自有一批方法在攻克
   - 按争议/开放问题组织（debate-driven）：适合领域内存在明显分歧或未解决的核心问题，综述本身承担"梳理分歧"的功能
4. 故事线设计：三段式张力
   - 现状（这个领域已经解决了什么）→ 局限（现有方法卡在哪，为什么这是真问题不是伪问题）→ 展望（你认为下一步该往哪走，为什么）
   - 这三段不是模板填空，局限段落必须具体到"哪些论文的哪个假设不成立"，不能是"仍有提升空间"这种空话
5. 从 `syntheses/` 到成稿：具体转化方法
   - `syntheses/` 里沉淀的是"论文之间的关系判断"，成稿需要的是"围绕一条论点组织这些关系"——这一步是重新排列，不是复制粘贴
   - 具体动作：先写一句话论点（这篇综述最终想让读者相信什么），再回头检查 `syntheses/` 里的哪些判断能支撑这句话，哪些其实是跑题的
6. 反模式清单
   - 罗列体（逐篇复述，无观点）
   - 大杂烩体（什么都提一句，没有取舍，读完记不住重点）
   - 无 gap 体（讲完现状直接展望，没有讲清楚"局限"这一环，展望显得没有依据）
7. 小结
   - 一句话：综述的价值不在于覆盖了多少论文，在于有没有一条别人没讲清楚的论点
8. 思考题/练习
   - 挑一个你已经攒了 `synthesis` 的子方向，先写一句话论点，再检查有没有材料支撑不起来这句话——写不出论点，说明还没读透

## B｜工具生态位对比：ReadR 该和谁一起用，而不是替代谁

**定位**：把 ReadR 放进整个"AI 辅助知识管理"工具谱系里横向对比，帮读者判断组合怎么搭，而不是单纯论证"ReadR 好在哪"。

1. 导读：你将获得
   - 一套划分知识管理工具的维度框架，不再是"哪个工具功能多"这种笼统比较
   - 几款代表性工具（Notion AI、Reflect/Mem、纯 RAG 类工具、llm-wiki、Zotero）在这套框架下各自的定位
   - 一个决策流程，帮你判断自己该用哪个、或者该组合哪几个
2. 划分维度
   - 知识作者是谁：AI 主导 vs 人主导
   - 组织单元是什么：自由笔记块 vs 论文条目 vs 向量嵌入
   - 输出目标是什么：wiki 本身 vs 综述产出 vs 单次问答
3. 逐个工具定位
   - Notion AI：自由笔记 + AI 摘要，无学术专属结构，胜在灵活，输了在没有强制的元数据约束
   - Reflect / Mem：AI 自动链接笔记，个人知识管理场景做得不错，但不是为学术论文场景设计，缺少 authors/datasets/benchmarks 这类学术实体
   - 纯 RAG 类工具（ChatPDF、Elicit 一类）：单篇论文问答能力强，跨论文的知识体系建构弱，是"查询时"工具不是"沉淀时"工具
   - llm-wiki：AI 主导的知识编译，覆盖速度快，精读深度浅（第一讲已详细对比过，这里简要重提，不重复展开）
   - Zotero + 插件生态：标注能力成熟，但标注和知识体系是两张皮（呼应开篇词）
   - ReadR：人主导，四层分工，终点是综述产出
4. 对比矩阵表
   - 维度：知识作者 / 学术元数据 / 精读支持 / 输出目标，逐个工具打分或简述
5. 决策流程
   - 问题一：你需要的是覆盖速度还是精读深度？
   - 问题二：你的终点是维护一个 wiki，还是要写出一篇综述？
   - 问题三：你现在的存量是在 Zotero 里，还是从零开始？
   - 根据回答给出组合建议，比如"Zotero 做标注存量 + ReadR 做知识体系 + NotebookLM 做产出"这类真实可行的组合，而不是"全部换成 ReadR"
6. 小结
   - 没有绝对最优工具，只有和你研究阶段匹配的组合
7. 思考题/练习
   - 对照决策流程走一遍自己的情况，写下你现在实际在用的工具组合，看看哪一环是缺失的

## C｜Obsidian 图谱视图专题：看见你没意识到的关联

**定位**：不只是操作教程，讲图谱视图作为认知工具的价值——为什么"看到关系"比"记住关系"更容易发现意外关联，用你自己的研究方向做真实案例。

1. 导读：你将获得
   - 图谱视图存在的认知价值：为什么视觉模式识别比文字检索更容易发现意外关联
   - 具体操作：按 tag/文件夹筛选子图，只看某个研究方向的网络
   - 一个真实案例：图谱视图怎么帮你发现了一个原本没意识到的研究关联
2. 为什么需要"看见"而不只是"记住"
   - wiki-link 拓扑（第二讲）建立的是关系的存在，但关系存在于 YAML 字段里，你不会没事去翻每条 entry 的链接字段
   - 图谱视图把这些关系变成空间布局——两个节点离得近、连线密集，这类模式人眼几秒钟就能捕捉到，靠读文字要慢得多
3. 具体操作
   - `Ctrl+G` 打开关系图谱视图
   - 按 tag 或文件夹筛选，只看某个方向的论文-概念-作者网络，避免全局图谱太乱看不出重点
   - 调整节点大小/连线粗细的显示设置，让核心节点更突出
4. 案例演示（需要你补充真实细节）
   - 在你自己 KG+LLM+Agent 方向的图谱里，找一次"意外发现"的具体经历：比如两个原本觉得不相关的子方向，通过某个共同概念节点连在了一起，这种连接在 entry 列表里很难注意到，图谱视图里一眼看出
   - **这一节需要你提供真实经历，具体是哪两个节点、发现了什么，草稿先留空/占位，不能替你编**
5. 局限：图谱视图不会自动给你 insight
   - 节点多了会变成一团乱麻，必须配合筛选才有用
   - 图谱视图只是把关系"摆出来"，看出这条连线代表什么、有没有价值，仍然要靠人主动去想——工具负责呈现，判断还是你的
6. 小结
   - 图谱视图是第二讲 wiki-link 拓扑"看得见"的那一面，价值不在于炫技，在于让意外关联有被看见的机会
7. 思考题/练习
   - 打开你自己的图谱视图，筛选出一个子方向，找一条你从没注意过的连接线，问自己：这条线连的两个节点，为什么会被关联在一起？

## D｜RSS 信息雷达设计：从"被动收推送"到"主动过滤噪音"

**定位**：RSS Dashboard 解决的是"发现新论文"，这一讲讲怎么设计订阅方案避免它变成又一个坟场。

1. 导读：你将获得
   - 一个反例：全订阅导致的信息过载，RSS 本身解决"发现"不解决"筛选"
   - 三层订阅分级方法：核心/外围/长尾
   - 一套具体的预筛流程，把 RSS 推送和 INGEST 阶段之间的空隙填上
2. 从一个反例说起
   - 把能想到的期刊和 arXiv 分类全部订阅，RSS Dashboard 里堆了几百条未读——这不是信息雷达，是把"读完就是坟场"从下载的 PDF 文件夹搬到了 RSS 未读列表，本质问题没解决
3. 三层订阅分级
   - 核心层：和你研究方向强相关的一两本期刊/会议,新推送必须过一遍标题（对照 README 里 IEEE Transactions 列表：TPAMI、TIP、TKDE、TNNLS、TMM、TCSVT，选和自己方向最相关的一两个，不是全订）
   - 外围层：arXiv 相关分类（cs.CV/cs.IR/cs.LG/cs.AI/cs.MM），只扫标题，不逐条细看
   - 长尾层：Papers With Code、Google AI Blog 这类精选源，偶尔翻一次，不设阅读压力
4. 具体方案演示：针对 KG+LLM+Agent 方向定制
   - 不是订阅所有和 AI 相关的源，而是按你实际的三个子方向（LLM-KG 融合、Agent-KG 系统、量化交易应用）拆开定制组合——比如量化交易方向额外加一个金融相关的 arXiv 分类或期刊源
5. 预筛流程：RSS 推送之后具体怎么处理
   - 固定一个时间窗口（比如每天 10 分钟），只看标题+摘要前两句，决定"拖进 to-read"还是"忽略"
   - 这一步其实是 INGEST 阶段之前还没被讲过的"预筛"动作——前四讲的动作序列是从"已经决定要读"开始的，这一讲补上"怎么决定要不要读"这一步
6. 小结
   - RSS 解决的是信息雷达的覆盖面，筛选逻辑要人自己设计，分级和预筛流程缺一不可，不然只是换了个地方堆着不读
7. 思考题/练习
   - 打开你现在的 RSS Dashboard，把订阅源按核心/外围/长尾重新分一次类，看看现有的哪些订阅其实早就该砍掉

## E｜NotebookLM 深度案例：一次真实的组会准备

**定位**：呼应加餐的叙事调性，比第 06 讲的功能概览更具体，用一次真实的组会准备过程复盘 NotebookLM 到底帮上了什么、哪里必须自己重写。

**重要提示：这一讲需要你提供真实细节才能写实——具体省了多少时间、生成内容里哪部分直接能用、哪部分被你整段重写。下面先给框架，真实素材需要你补充，我不会替你编造数字或细节。**

1. 开场：一次真实场景
   - 组会前一天，决定用 NotebookLM 试一次而不是纯手工做 PPT
2. 具体步骤
   - 建笔记本，加入这段时间精读的几篇论文
   - `notebooklm generate slide-deck` 生成初版
   - 对照生成结果，哪些部分直接能用（预计：论文对比表格式化这类结构性内容），哪些必须重写（预计：你自己的观点、和当前研究的关联这类判断性内容）
3. 时间对比
   - 纯手工做 PPT 大概花多久，用 NotebookLM 生成初稿+手工改大概花多久——需要你回忆真实数字，不能是"效率提升 50%"这种编造出来的比例
4. 播客/思维导图有没有用上
   - 如果生成过 audio 模式的播客，具体在什么场景用的（比如通勤路上复习），效果怎么样
5. 复盘
   - 呼应第 06 讲的核心论点——"信息转格式不等于判断"，用这次真实经历验证这条论点成不成立：生成内容里最终被保留的部分，是不是刚好都是"格式转换"类的，被重写的部分是不是刚好都是"判断"类的
6. 小结/收尾
   - 一句话总结这次真实经历给出的结论

## F｜团队协作专题：把这套方法论教给整个课题组

**定位**：呼应你在组会分享、推荐给研 0 朋友这条线，从"个人怎么用"扩展到"课题组怎么共用一个 vault"。

1. 导读：你将获得
   - 团队共用知识库比个人使用多出来的两个具体问题：写入冲突、新人上手成本
   - 一套可行的 Git 协作模式
   - 一份新人 onboarding 的最小闭环设计
2. 团队场景比个人场景复杂在哪
   - 多人同时新增 entry 容易产生冲突
   - 每个人对 tags schema 的理解会逐渐漂移，个人用的时候第二讲讲过这个问题，团队场景下会被人数放大
3. Git 协作模式
   - 按人建分支，定期合并，减少同时编辑同一文件的冲突概率
   - 或者按子方向拆文件夹，天然减少交叉编辑
   - `scripts/ReadR.ps1 -Validate` 这类校验脚本在多人协作场景下的价值：合并前先跑一遍，检查 YAML 和必填字段有没有被破坏
4. 权限设计
   - NotebookLM 的 `share` 功能：谁能编辑笔记本、谁只能看,配合团队分工用
5. 新人 onboarding：最小闭环
   - 不要求新人一上来就理解四层架构的全部道理，先带他跑一遍 INGEST → BROWSE 的最小闭环（至少一篇论文），体感建立之后再补方法论
   - 可以直接复用开篇词、01 讲作为新人第一天的阅读材料
6. tags 一致性维护
   - 团队场景下建议指定一个"标签负责人"角色，定期检查有没有新标签和已有标签重复表达同一个意思，及时合并
7. 小结
   - 团队协作的核心不是加更多规则，是把个人场景已经验证过的分工原则（人主导判断，工具负责机械操作）复制到多人场景，同时多加一层"减少写入冲突"的机制
8. 思考题/练习
   - 如果你要现在就把这套方法论介绍给一个新入学的研 0，你会让他第一天做的第一件具体的事是什么？
