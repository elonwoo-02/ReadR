# Google 刚发的新格式，和我琢磨了半年的东西撞车了

## 你将获得

- Google Cloud 新发布的 OKF v0.2 具体是什么，它和 ReadR 之间的架构相似性从哪来
- 两者真正的分歧在哪——不是谁做得更好，是"格式"和"流程"这两个不同层面的问题
- 一份可以直接抄的具体方案：怎么让 ReadR 的知识库变成一份 OKF 兼容的知识包

## OKF 是什么

七月二十五号，Google Cloud 给它旗下的 Open Knowledge Format（OKF）发了一次大版本更新，升到 v0.2。OKF 是 Knowledge Catalog（前身是企业数据目录产品 Dataplex）里放出来的一份开放规范：用纯 markdown 文件加 YAML frontmatter 表示知识，按目录层级组织，不绑定任何特定的 Agent 框架或模型厂商。仓库里带了两个参考实现——一个基于 Google Agent Development Kit、用 Gemini 做后端的 Enrichment Agent，能自动从 BigQuery 之类的数据源爬取元数据、生成知识包；一个用 Cytoscape.js 做的力导向图谱可视化工具，生成一个自包含的 HTML 文件，不需要额外安装就能在浏览器里打开看图谱。

纯 markdown、YAML frontmatter、目录层级、图谱可视化——这套底层选择和 ReadR 几乎一致，只是 OKF 面向企业数据表和数据集，ReadR 面向学术论文。

## 架构上的重合

OKF 的 SPEC 专门有一节讲"这个格式和什么类似"，明确提到了 **LLM wiki 仓库**——用 markdown+frontmatter 做 Agent 可读知识库这套思路——以及 Obsidian、Notion 这类工具。这条脉络和 ReadR 的来源是同一条：ReadR 是从 Karpathy 那套三层 llm-wiki 架构改造来的，一个走向企业数据目录，一个走向学术文献管理，是同一套底层思路在两个领域的独立应用。

两边都靠**显式链接**建立知识之间的关系，而不是靠向量检索的相似度。OKF 的每个 concept 之间用标准 markdown 链接互相指向，链接的具体语义（父子关系、引用关系，还是别的什么）由链接周围的文字说明，而不是链接本身的类型——这和 ReadR 第二讲讲过的 wiki-link 拓扑是同一套逻辑,只是 OKF 把这条规则写进了正式规范。

两边都容忍"没写完"的状态。OKF 明确要求消费者必须容忍断链——指向不存在概念的链接不算格式错误，可能只是还没被写出来的知识；ReadR 里 `concepts/` 条目允许先占位、以后再补，逻辑一致：知识库不是一次性建完的，是持续生长的。

一个独立于 ReadR、由 Google 一整个团队做出来的项目，在完全不同的领域里，得出了几乎一样的架构判断——这至少说明,markdown+frontmatter 这套底层选择,不是个别项目的偏好,是这类问题的自然解。

## 真正的分歧

分歧比相似点更值得展开。最根本的一条：**OKF 解决的是"格式"问题，ReadR 解决的是"流程"问题**。OKF 的 SPEC 明确写了"非目标"——不定义固定的概念分类体系，不规定存储或查询基础设施，不替代领域专用 schema。它是一份纯粹的存储协议，谁来写、什么时候写、写完要不要审核，OKF 不管。ReadR 恰恰相反——四层架构的核心不是"文件该怎么存"，是"INGEST/BROWSE/CLOSE-READ/REVIEW 这四个阶段谁该做什么"，格式只是这套流程的载体。

这条分歧背后，是两边对"知识由谁生产"的默认假设不同。v0.2 的更新说明写得很直接：知识语料库不再是一次写成然后被动阅读，而是持续被 Agent 生成和维护——当大部分内容是机器生成的，下游系统需要办法判断该信多少。所以 v0.2 加了一整族"信任信号"字段：`generated`（谁生成的、什么时候）、`verified`（有没有被确认过，consumer 据此推导出"未验证/机器已确认/人工已审核"三档信任等级）、`sources`（这条知识的出处）、`status` 和 `stale_after`（是否还新鲜）。本质上是**事后**给每条知识打一个信任标签。

ReadR 的做法是**事前**门禁：annotations 里"个人评价与思考"必须人写，reviews 层的论点和结论 AI 完全不碰——不是靠标签标注"这条内容可信度多高"，是根本不允许 AI 单独产出这类内容。

两种解法都在回答同一个问题——AI 生成的知识,怎么知道该信多少——给出的答案完全相反：一个在生产端设卡，一个在消费端打标签。

## 具体能怎么用

OKF 这套信任字段可以直接补进 ReadR 现在的空白。ReadR 的 `status: to-read/browsed/close-read` 记录的是阅读深度，跟 OKF 的 `verified` 记录"有没有人把关过"是两个不同的轴——BROWSE 阶段 AI 自动提取的概念、作者这些条目，目前在 ReadR 里没有单独标注"这是 AI 起草的、还没人看过"还是"AI 起草、人已经确认过"。加上 `generated`/`verified` 这两个字段，成本很低，换来的是这个状态第一次变得可查询、可过滤。

反过来，ReadR 也能给 OKF 生态提供一个具体参照——annotations 层的强制人工门禁,是一个跑过几个版本验证的案例，说明门禁和标签这两条路子可以叠在一起用,不是非此即彼。

落地步骤：给 `library/entries/` frontmatter 补一个 `type` 字段（比如 `type: Academic Paper`），让整个知识包变成一份 OKF 兼容的 bundle；把 `generated`/`verified` 接进 BROWSE 阶段的自动化流程，AI 起草时自动写 `generated`，人工确认后补一条 `verified`；annotations/reviews 层的人工门禁保持不变，这是 ReadR 比 OKF 更严格的部分，没必要放松。做完这几步，ReadR 不用换底层格式，还能顺带获得"任何 OKF 消费端都能读懂它"这个副产品。

## 小结

Google 用一整个团队、一份正式规范，回答了和 ReadR 同一个问题，给出的答案却是反过来的：一个信奉生产前把关，一个信奉生产后打标签。
